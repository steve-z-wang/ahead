# Controller

Encode and decode protocol messages; manage connections, invoke application-provided authentication, coordinate channel subscriptions and stream changes.

Current code: [server/live.rs](../../../../../crates/server/src/live.rs) (`decode_subscribe`, `negotiate`, `pull`, `page_progress`); per-socket state machine `serveLive` and the `WakeHub` subscription in [server/index.mts](../../../../../packages/server/index.mts).

## 1. Introduction and Goals

- Hold one WebSocket per client, learn its channels once, and push each new page for those channels as soon as a transaction that touched them commits.

## 3. Context and Scope

- Input: an authenticated socket from [Transport](transport.md); commit wakes from [Notify](../engine/notify.md).
- Output: the `subscribed` acknowledgement and [Pull](../../protocol/pull.md) pages ([Protocol / Subscriptions](../../protocol/subscriptions.md)).
- Dependencies: `negotiateLive` and `pullLive` each run in a database transaction through [Backend interface](../backend-interface.md); `onCommitted(scope, wake)` registers with the `WakeHub`.

## 5. Building Block View

- Handshake: wait for the first frame (any later frame closes the socket with `1002 subscribe is the only client frame`); `negotiateLive` decodes and normalizes scopes and reads each head inside a transaction; the reply is sent only after wakes are registered.
- Per-scope state `{scope, fromCursor: head, pending, running, closed}`; `drain(state)` runs at most once per scope at a time: while `pending`, call `pullLive(owner, scope, fromCursor)` repeatedly, send the page when `toCursor` advanced, move `fromCursor`, stop when the page is not full; a wake during a drain sets `pending` and a trailing drain runs.
- Initial drain: every scope is marked pending right after the acknowledgement, so commits between the negotiation transaction and wake registration are not missed.
- Failure: any drain error goes to `onError` and closes the socket with `1011 server`; handshake errors close with `1002` for `request.invalid` or `1011` otherwise; cleanup removes every wake registration and listener.
- Pages are generated by the same `process_pull` as HTTP ([Server Pull](../engine/pull.md)), so the client applies both through one path.

## 6. Runtime View

- Commit → `WakeHub.notify(channels)` → each socket subscribed to a channel drains → one `pullLive` transaction per socket per channel → page frame.
- A duplicate push (cached receipt) touches no channel and wakes nothing.

## 11. Risks and Technical Debt

- **Potential risk: fan-out cost is one pull transaction per subscriber per commit.** N sockets on one channel run N `pullLive` transactions (head, scan, loaders) for every commit that touches it; there is no shared page cache. Evidence: `drain` in `serveLive`. Not measured ([#12](https://github.com/zanminwang/ahead/issues/12)).
- **Confirmed limitation: single-process wake domain.** A socket is woken only by commits in its own process ([Notify](../engine/notify.md)).
- **Confirmed limitation: no resubscribe, no bounded scope count.** Changing channels requires a new socket; a subscribe frame may name any number of scopes and each gets a wake registration. Evidence: `serveLive`, `decode_subscribe`.
- **Confirmed gap versus the target: the state machine is TypeScript.** Rust owns decoding, negotiation and page validation; connection lifecycle and drain scheduling live in [server/index.mts](../../../../../packages/server/index.mts), so a second server runtime would re-implement them.
